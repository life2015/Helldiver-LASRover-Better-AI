# 验证记录与迭代计划

## 当前能作出的结论

截至 2026-09-18，0.3 在已测试的激光漫游车战斗场景中实现了更频繁换目标。用户确认会在敌人尚未死亡时转火，运行计数和外部观察支持这一行为。较高难度、更多怪物的第二场景中也持续运行。

尚未证明每次请求都导致转火、每个目标都已点燃、精确光束命中时长、所有敌人/阵营兼容、联机所有权场景或性能影响。以下数字是记录，不是统计显著性实验或全面兼容认证。

## 证据分层

| 证据 | 可以说明 | 不能单独说明 |
| --- | --- | --- |
| 离线原生代码分析 | 选敌函数、字段及评分因子之间的关系 | 运行时一定按预期生效 |
| 合成内存 fixture | 读取逻辑和边界处理符合当前结构假设 | 结构假设就是所有版本的真实布局 |
| 实机只读采样 | 本次对象归属、目标和候选字段可读且一致 | Mod 已经改变了行为 |
| 安装后运行计数 | 请求提交、请求期间的目标变化 | 命中、点燃、严格因果关系 |
| 用户观察 | 本次游玩明显更频繁转火 | 定量点燃率、所有敌人覆盖或 FPS |

## 离线验证基线

`scripts/test.py` 当前共41项：核心21项、初始化6项、快照14项，包含窗口、单目标、避免两目标往返、时间不连续、身份复用、读失败、部分写回滚、启动后恢复、任务状态缺失等情况。打包还执行实际编译入口、音频回调保持、重复 guard、归档往返和 ZIP 完整性检查。

这些测试不调用游戏原生选敌函数，也没有跑真实战斗引擎。测试列表应随着实际改动更新，不应把41这个数字作为必须保持不变的目标。

## 建议的迭代顺序

先保持0.3作为可回退基线，补充场景标注和按请求的事件记录，再评估是否调窗口。为诊断增加请求 ID、屏蔽/允许目标、触发原因、恢复原因、耗时会比单纯增加累计计数更有帮助。

如果以后要做“确认点燃后才转火”，这是新增需求：必须识别正确状态组件、施加者/持续时间、过期及复制语义，重新验证性能与联机行为。不能把当前0.4秒近似条件改个名称就声称实现了状态检测。

每次实验只改变能解释的条件，记录旧/新包、场景、用户观察及对应采样。若失败，保留错误证据并回退，不覆盖旧成功包或把未验证的猜测写成确定结论。
