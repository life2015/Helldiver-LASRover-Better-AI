# 盾虫持续锁定：反馈与计时排查

记录于2026-09-19。检查对象为当前0.7.2源码，用户称使用“最新包”，尚无反馈者的ZIP哈希、渠道、HUD变体或当次日志。本次不修改运行时代码、不重新打包、不部署游戏。

后续变更：0.7.3按用户要求将未进入攻击状态的超时延长到1.5秒；下文0.5秒、源码哈希及合成输出保留为0.7.2调查证据。本次时长调整没有实现独立最长占用计时，不能作为盾虫锁定问题的已确认修复。

## 已知情况与结论边界

用户反馈有时持续锁定盾虫（Hive Guard），周围仍有其他活敌。是否始终为同一个实体ID、请求计数是否增长、其他活敌是否进入原生可用候选，均未知。

[Hive Guard词条](https://helldivers.wiki.gg/wiki/Hive_Guard)描述其头部和腿部中甲，以及保护身体的防御姿态；查询时页面直读返回403，通过搜索索引取得描述。该资料可以解释正面攻击受护甲影响的可能性，不能说明本Mod的实际运行分支，也不能证明某次激光命中部位或点燃结果。

当前转火不读取伤害、护甲、命中或点燃状态。`snapshot.lua`的`synced`来自行为目标、瞄准目标和行为标志，**不是造成伤害的标志**。即使攻击被护甲挡住，只要节点7且同步状态持续约0.4秒，并有其他有效候选，策略仍会提出转火计划。

所以不能归因为“伤害被挡住，伤害计时不走”：代码没有伤害计时。也不能排除敌人姿态、瞄准或原生状态转换间接影响转火；需要当次采样确认。

## 已离线复现：两种计时互相清零

`policy.lua`采用两个连续窗口：

- 节点7且同步时累计`elapsed`，清空`idle_elapsed`；约0.4秒后走`attack_window`。
- 节点6，或节点7但不同步时累计`idle_elapsed`，清空`elapsed`；约0.5秒后走`lock_timeout`。
- 进入另一种状态的首个采样不累计时间；目标/身份变化、长采样间隔、缺失快照等也会重置。

这存在可复现的计时盲区：同一目标在两种状态间反复短暂切换，每段都不足窗口，可能一直没有计划。它不限于盾虫，也不要求读取伤害。

隔离Lua state中调用当前真实`policy.lua`，固定同一无人机/目标身份和两个有效候选，以16Hz输入10秒；交替场景每0.25秒切换状态。仅在计划出现时调用`committed`，没有真实控制器、内存写入或原生选敌执行。

| 合成输入 | 首次计划 | 10秒内计划数 |
| --- | --- | --- |
| 始终节点7且同步 | 0.4375秒，attack_window | 22 |
| 始终节点7但不同步 | 0.5秒，lock_timeout | 20 |
| 节点7/6每0.25秒交替 | 无 | 0 |
| 保持节点7，synced每0.25秒交替 | 无 | 0 |
| 始终节点7且同步，但没有替代候选 | 无，预期行为 | 0 |

两种交替场景的攻击/未攻击计时最大值均为0.1875秒。16Hz采样使0.4秒阈值首次在0.4375秒被观察到，这不是计时误差证明。计划数不是游戏中提交的请求数，更不是转火次数。稳定攻击输入不含命中/伤害字段，只证明策略没有这种依赖。

本地复现脚本和结果为`build/hive-guard-diagnostic-20260919.py`及同名JSON。检查时policy.lua的SHA-256：`2898e6967d854f81f90899541fcbf2594f0cd200d9edf6dc8a7670666e7f0919`。build目录不要求纳入公开仓库；维护者可在开发文档说明的Lua测试宿主中运行下面的最小复现：

```lua
-- ROOT由scripts/lua_host.py宿主设置为仓库根目录。
local P=assert(loadfile(ROOT..'/src/policy.lua'))()
local state={}
local s={key='synthetic-rover',target=1,node=7,synced=true,candidates={
    {id=1,identity='entity-1',eligible=true,distance2=100},
    {id=2,identity='entity-2',eligible=true,distance2=25}}}
local plans=0
for step=0,160 do
    s.node=math.floor(step/4)%2==0 and 7 or 6
    local now=step/16
    local plan=P.plan(state,s,now)
    if plan then plans=plans+1;P.committed(state,plan,now) end
end
return tostring(plans) -- 当前0.7.2为0；修复后应重新定义预期。
```

这是代码层面已证实的盲区，**尚未证实它就是这次盾虫反馈的根因**。既有118项Lua通过记录没有覆盖这种持续交替输入，不构成反证。

## 如何区分实际原因

| 卡住期间的证据 | 优先排查 |
| --- | --- |
| 同一个target，requests不增长，node/synced短暂反复变化 | 两种计时被重置；还要排除读取间断或实体身份变化 |
| requests不增长，decision为no_alternative | 活敌未成为其他有效候选；原生候选需实体身份、来源标志、阵营及正评分通过，肉眼可见不等于可选 |
| requests持续增长，target不变，rotations不增长 | 已提出请求，但原生未在请求观察期间完成目标切换；需查候选变化、请求期限及恢复原因 |
| decision为precondition_changed或长期waiting | 写入前条件变化或采样不可用，不能按正常攻击计时解释 |
| stopped或cleanup_pending | 优先查停止原因和清理状态，见调试手册 |

HUD的Locked只有同步时才显示，Next也可能为(last)历史请求。应同时比较目标ID、计数增量及实际激光方向。主日志约2秒覆盖写，单张HUD或单份日志无法排除每0.25秒的状态切换；复现场景优先用[外部只读采样](debugging.md#外部只读采样)保存时间序列。`eligible`计数含当前目标且可能有重复条目，不是不同替代敌人数。

反馈方不必先判断中甲或敌人类别；至少保留包身份、复现时间、其他敌人在场的画面及当次日志。不能用本机旧日志冒充反馈者现场。

## 修正方向（调查时提出，后由0.7.4实现）

为同一有效实体增加独立的最长占用窗口，使短暂攻击/未攻击切换不再无限重置总进度。仍限定已验证的节点6/7、连续有效采样及其他有效候选；换实体、离开相关行为阶段、快照失效和长间隔仍需重置。达到兜底窗口时只提出既有安全转火请求，不直接改目标ID或扩大可写范围。

具体阈值需要和正常转向、短暂遮挡、单目标、身份复用及原生拒绝请求分别验证。此改动针对已复现的计时盲区，不能保证修复“原生候选没有其他敌人”或“已请求但原生没有切换”的情况。无需为了处理该盲区引入伤害/点燃读取或盾虫类型硬编码。

## 0.7.4修正与验证

独立`lock_elapsed`累计节点6/7、身份连续有效的同目标观察时间；不随攻击或同步状态变化清零。阈值1.5秒，普通0.4秒攻击窗口优先生效；连续未攻击1.5秒沿用原原因，其他超时为`lock_max_duration`。两种兜底均排除当前目标、忽略Recent、按距漫游车最近的有效候选请求，无距离则退回原生在筛选池内选择。

换目标/实体/无人机、缺失身份或快照、离开节点6/7、采样间隔超过0.25秒或时钟倒退会重置。成功提交请求后重新观察计时，避免请求后马上再次提交；没有替代候选不强制切换。没有新增原生调用或内存写入种类，也没有盾虫类型硬编码。

原先两种每0.25秒切换的序列现在均在1.5秒出现计划；边界、普通攻击优先、Recent忽略、坐标缺失、身份与采样重置、单目标不干预、提交后重计、控制器恢复及HUD原因区分共新增9项测试。总计127项Lua测试通过。原0.7.2复现表与哈希保留为历史证据，不能当作0.7.4输出。尚未确认反馈者现场是否属于同一原因，实战待验收。
