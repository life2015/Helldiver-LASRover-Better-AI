## 当前不应被误认为已经完成的事

目前是本地实验项目和维护资料，尚未建立完整的独立开源发布流程。未为 Rover 项目选定许可证；检查到的两个上游 `THIRD_PARTY.md` 也写明未选择仓库级许可证。因此不要因为源码可查看或其 LuaJIT 依赖采用 MIT，就给所有复用代码自动标为 MIT。

后续公开前需要整理各部分来源和使用许可，决定本项目原创部分的许可证，并确认打包材料的分发安排。这份文档记录当前缺口，不替维护者作许可选择。尤其要区分源代码、第三方加载器和其中原游戏音频回调的来源。

## 独立仓库应先整理什么

1. **显式化目录依赖**：`package.py` 现在直接导入同级 `SentryAimRetention/scripts/archive.py`；`observe.py` 直接导入同级 `research/observe_rover.py`。采用明确固定的依赖方式，或在来源许可明确后整理为项目内模块，保留署名和版本。
2. **统一版本信息**：当前版本号、游戏哈希和签名分散在入口、打包、部署及观察代码。集中为有校验的配置，避免出现“日志版本更新但部署器仍校验旧版本”的混合状态。
3. **持久化部署记录**：现在卸载依赖被忽略的 `build/deployment.json`；未来应避免构建清理误删它，并校验记录的游戏目录与操作目录一致。
4. **处理观察器数据入口**：公共测试保留合成 fixture，不依赖个人内存快照；保留如何生成本地证据的说明。
5. **干净环境复现**：从没有 `build/` 和 `releases/` 的目录开始，按开发文档取得固定输入、运行测试和打包。当前没有无游戏安装的完整 CI 路径，因为测试使用游戏自带 Lua DLL。

这些是后续重构建议，本轮仅整理文档，没有暗中替换依赖、设置许可证或改动已安装的0.3。

## 源码与本地材料的边界

适合进入源码评审的内容：项目源码、脚本、合成测试、文档、经过核对的来源说明，以及不含个人地址/原生代码的大致统计结论。

现有 `.gitignore` 忽略 `build/`、`releases/`、`__pycache__/`；同级 `research/.gitignore` 忽略 `artifacts/`、`tools/` 等。公开前还应检查实际待提交文件，不只相信忽略规则。以下保持为本地输入或单独审查的发布材料：

- 游戏 EXE、DLL、加载后模块快照、原生反汇编、崩溃转储。
- 稀疏内存 trace、带绝对地址或个人环境信息的原始日志。
- 本机部署记录、个人目录和工具缓存。
- 下载的加载器 ZIP、生成的 Lua 字节码和游戏资源归档。

源码发布与预编译 Mod 发布是两项不同的交付。当前 package report 标明 `local_private_build=true`；文档写全并不自动改变这一状态。

## 维护变更的验收方式

提交说明先写清触发条件和行为变化，例如“启动管理器尚未出现时从永久停止改为等待重试”，再写证据。策略变更、布局迁移、生命周期修复应分别验证，避免把它们混成一次难以归因的实验。

原生地址变更需要可追溯的版本和推导说明；策略修改需要能区分新旧行为的测试；恢复代码修改必须覆盖身份复用、引擎覆盖和部分失败；启动改动要执行真正编译后的入口，不能只 mock 模块已加载。

不要在文档、测试或报告里把未测的事情标记为成功。对已有包追加实测证据应建立独立记录并引用包 SHA，而不是修改包内 provenance 后仍称其为同一个被测包。
